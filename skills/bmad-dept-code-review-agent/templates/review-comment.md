## GitHub-format notes

When `--comment-format github` is selected, render each comment block as
a GitHub PR review comment:

- Anchor via the GitHub REST API's `pulls/comments` shape:
  `path={{FILE_PATH}}`, `line={{LINE_NUMBER}}`, `side="RIGHT"`,
  `body=<comment body markdown>`.
- The ` ```suggestion ` fence renders as a one-click "Apply suggestion"
  in the GitHub UI — only emit it for mechanical fixes.
- Group all comments for a single PR into one "Start a review" batch
  rather than posting them as individual immediate comments, so the PR
  author sees them as one review pass.
- Prefix the comment body with the severity icon + category so it's
  scannable in GitHub's review-comment list view.

## GitLab-format notes

When `--comment-format gitlab` is selected, render each comment block as
a GitLab MR discussion thread:

- Anchor via the Discussions API `notes` shape:
  `position[new_path]={{FILE_PATH}}`, `position[new_line]={{LINE_NUMBER}}`,
  `body=<comment body markdown>`.
- Use GitLab's suggestion syntax ` ```suggestion:-0+0 ` for
  single-line replacements (the `-0+0` offsets mean "replace exactly this
  line" — adjust offsets for multi-line suggestions per GitLab's syntax).
- Each comment becomes its own discussion thread — GitLab does not batch
  comments into a single review the way GitHub does, so group by file in
  the written-file ordering to keep related comments visually adjacent.

## Inline-markdown-format notes (default)

When `--comment-format inline-markdown` is selected (the default), the
blocks above render as-is — plain markdown, `file:line` as the anchor
text, no platform-specific payload shape. This is the safest default
when the target forge isn't named: paste directly into a PR description,
a Slack thread, a ticket, or any tool-agnostic review surface.
