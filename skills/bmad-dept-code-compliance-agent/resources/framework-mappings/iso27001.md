# Framework mapping guide — ISO 27001

## What ISO 27001 requires

**ISO/IEC 27001** is the international standard for an **Information
Security Management System (ISMS)** — a systematic, risk-based
management approach to protecting information assets, published
jointly by ISO and IEC. Organizations can be independently **certified**
against it by an accredited certification body, which makes it one of
the most commonly requested "prove your security posture" artifacts in
enterprise vendor-risk questionnaires globally (broader adoption
outside the US than SOC 2, and often requested alongside it).

The standard itself (the numbered clauses, 4–10) specifies **what the
ISMS must do** — establish context, show leadership commitment, plan,
support, operate, evaluate, and improve. **Annex A** then lists a
catalog of security controls an organization selects from (via a
documented **Statement of Applicability**) to address the risks
identified in its risk assessment. Critically: **Annex A controls
themselves are not individually certified** — the ISMS process
(clauses 4–10) is what's audited; Annex A is a reference control set,
not a checklist every organization implements identically.

This means an ISO 27001 control-mapping from code findings alone can
**never** constitute meaningful ISO 27001 coverage on its own — it can
only speak to the narrow **technical-controls subset** of Annex A that
happens to be code-observable. The majority of Annex A, and the entire
clause 4–10 ISMS process, requires a human-run management system this
agent cannot see or substitute for.

Current published version: **ISO/IEC 27001:2022** (restructured Annex A
from the 2013 edition's 14 domains into 4 themes).

## Control taxonomy

Annex A:2022 organizes its controls into **4 themes**:

| Theme | Focus | Approx. control count |
|---|---|---|
| A.5 Organizational controls | Policies, roles, supplier relationships, incident management, business continuity | 37 |
| A.6 People controls | Screening, terms of employment, awareness/training, disciplinary process | 8 |
| A.7 Physical controls | Physical security perimeters, equipment, secure disposal | 14 |
| A.8 Technological controls | Access control, cryptography, secure development, vulnerability management, logging | 34 |

## Per-stack applicability for ISO 27001

| Stack | Applicability (A.8 Technological controls subset) | Why |
|---|---|---|
| All 8 stacks | **Heavy** for A.8.2, A.8.3, A.8.5, A.8.9, A.8.24, A.8.25, A.8.28, A.8.29 | These technical/secure-development controls apply uniformly wherever source code exists, same reasoning as CIS Controls' code-observable subset. |
| All 8 stacks | **None** for A.5 (Organizational), A.6 (People), A.7 (Physical) themes | These 59 of 93 controls are entirely outside code visibility — always mark N/A for code-mapping purposes with a pointer to the ISMS owner (typically an Information Security Manager or the ISO 27001 Lead Implementer). |

Like CIS Controls, ISO 27001 applicability doesn't vary meaningfully
by stack for the code-observable subset — it varies by **theme**
instead. Roughly **two-thirds of Annex A (A.5, A.6, A.7) is
categorically out of this agent's reach on every project, every
stack.**

## Evidence requirements for ISO 27001

- **A.8.2/A.8.3 (Access control):** least-privilege enforcement,
  role-based access checks present on privileged operations.
- **A.8.5 (Secure authentication):** no hardcoded/shared credentials;
  strong authentication mechanism evidenced in code.
- **A.8.9 (Configuration management):** hardened defaults, no exposed
  debug/management endpoints.
- **A.8.12 (Data leakage prevention):** no sensitive data in logs,
  error messages, or client-side-exposed responses.
- **A.8.24 (Cryptography):** TLS enforced, no disabled certificate
  validation, strong randomness for tokens/keys.
- **A.8.25/A.8.26/A.8.28/A.8.29 (Secure SDLC):** absence of classic
  weakness classes, PLUS evidence the DCA suite itself (audit,
  sonar-scan, code-review, compliance) is run as part of the
  development lifecycle — this agent's own `audit-trail` artifact is
  directly relevant evidence here.
- For the A.5/A.6/A.7 themes: evidence requirement is explicitly
  "not assessable by this agent" — always point to the organization's
  Statement of Applicability and ISMS documentation as the real
  evidence source; never fabricate organizational-control evidence.

## Common gaps DCA CAN auto-detect

- Missing/insufficient access-control and privileged-access enforcement (A.8.2/A.8.3).
- Hardcoded credentials, weak authentication patterns (A.8.5).
- Exposed debug/management endpoints, unhardened configuration (A.8.9).
- Sensitive data in logs or error output (A.8.12, inverted signal).
- Disabled TLS/certificate validation, weak cryptographic randomness (A.8.24).
- Classic secure-coding weakness classes — injection, XSS, deserialization (A.8.28).
- Stale/vulnerable dependencies when a manifest is present (A.8.8).
- Presence (or absence) of a security-testing cadence via the DCA findings-cache run history (A.8.29, partial/corroborating).

## Common gaps DCA CANNOT auto-detect (human review required)

- Whether a Statement of Applicability (SoA) exists and correctly scopes which Annex A controls apply.
- Whether an ISMS risk assessment and treatment plan (clause 6) has been performed and is current.
- Leadership commitment and information-security policy documentation (clause 5 / A.5.1).
- Supplier/third-party relationship security requirements and review cadence (A.5.19–A.5.23).
- Incident-management process existence and testing (A.5.24–A.5.28).
- Business continuity and disaster-recovery plan existence and testing (A.5.29–A.5.30).
- Personnel screening, terms of employment, security-awareness training completion (A.6 theme, entirely).
- Physical security perimeter, equipment security, secure disposal practices (A.7 theme, entirely).
- Internal audit program existence and findings-closure tracking (clause 9.2) — this agent's own audit-trail can be ONE input, not a substitute for the full internal-audit program.
- Management review cadence and continual-improvement process (clauses 9.3, 10).

## Worked mapping example for ISO 27001

Given findings from a merged `audit` + `sonar-scan` run:

```
F1: SPRING-SEC-007 "Actuator /env exposed without auth" — HIGH
F2: SPRING-SEC-010 "Hardcoded DB password in application.yml" — CRITICAL
F3: APPB-SEC-003 "Full user object logged at INFO level" — HIGH
```

Resulting control-mapping rows:

| Annex A control | Status | Mapped finding(s) | Remediation note |
|---|---|---|---|
| A.8.9 Configuration management | gap | F1 | Restrict/authenticate the Actuator endpoint per environment-hardening baseline. |
| A.8.5 Secure authentication / A.8.24 Cryptography | gap | F2 | Move credential to a secrets manager; rotate the exposed password. |
| A.8.12 Data leakage prevention | gap | F3 | Redact sensitive fields from the log statement. |
| A.5.1 Information security policy | N/A (not code-observable) | — | Confirm the organization's ISMS documentation covers this service; owner: Information Security Manager / ISMS Lead. |
| A.6.3 Security awareness training | N/A (not code-observable) | — | Owner: HR/Security training program — entirely outside this agent's reach. |

## Attestation considerations for ISO 27001

Formal ISO 27001 **certification** is issued only by an **accredited
certification body** following a two-stage external audit (Stage 1
documentation review, Stage 2 implementation audit), with annual
surveillance audits thereafter. This agent's `ATTESTATION.md` output
is never a substitute for that certification — it is, at most, a
technical evidence contribution an **Information Security Manager** or
**ISMS Lead Implementer** might compile as part of internal Stage-1/2
audit preparation, or as supporting evidence for the Statement of
Applicability's technical-controls section. Name the signer explicitly
as "Information Security Manager" / "ISMS Lead" — never imply an
accredited certification body's audit opinion is satisfied by this
document.
